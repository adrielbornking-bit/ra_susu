# R&A SUSU LTD

Next.js 15 App Router application for a Ghanaian Susu group, using TypeScript, Tailwind 3, a shadcn-style Radix button component, Framer Motion, Recharts, Auth.js credentials and Prisma with Neon PostgreSQL. Hosting target: **Render Node web service**.

## Start locally

Use the latest maintained Node 22 LTS patch release (22.16 or newer). From this folder:

```bash
npm ci --include=dev
cp .env.example .env
```

Fill in `DATABASE_URL`, `DIRECT_URL`, `AUTH_SECRET`, `CRON_SECRET` and `ADMIN_PHONE` in `.env`. Generate separate secrets using `openssl rand -base64 32`. Use Neon’s pooled connection for `DATABASE_URL` and its direct connection for `DIRECT_URL`, both with TLS (`sslmode=require`). No database credentials are included.

```bash
npm run db:migrate
npm run db:seed
npm run db:import
npm run dev
```

Open `http://localhost:3000`. `/preview` is a read-only design preview with clearly labeled sample data. `/dashboard` uses the real database and requires authentication. The public landing-page statistics show real aggregate records when the database is available; an unavailable statistic is a dash, never an invented number.

## Initial admin

- Username: `superadmin`
- Email: `admin@ransusu.com`
- Role: `SUPER_ADMIN`
- Phone: your `ADMIN_PHONE` in international format, e.g. `+23324…` (a real, unique 12-digit international number).
- Password: randomly generated by the seed command, displayed once in its terminal output. Store it securely.

The admin can sign in using username, email or phone plus password, leaving verification token blank. The first dashboard visit requires changing the temporary password. Password changes revoke existing sessions; sign in again afterwards. The database enforces a single super admin. Running the seed again never overwrites an existing admin password. To recover the admin from an authenticated Render shell, run `npm run db:recover-admin` and change its new temporary password immediately.

Use an admin phone that does not belong to one of the 11 participant records. If you deliberately use an imported member’s phone for the admin, that phone will identify the admin and the importer skips it rather than creating a duplicate identity.

## Spreadsheet import

`prisma/seed-data.json` contains the **11 validated participant records** extracted from `SUSU data collection.xlsx`. The misspelled `Phione number` header was mapped to phone; domestic numbers were normalized to `+233…`. Source ID placeholders are not used as internal identifiers. `prisma/import-report.json` records the result.

The spreadsheet has no next-of-kin phone column. Those values are `null`; they are not invented. Source names and next-of-kin text are retained for admin review. No members are automatically approved and no slots are assigned by importing.

`npm run db:import` seeds the admin and initial 20 slots, then inserts only phones that do not already exist. Existing users are never overwritten. Keep this repository private because the seed file contains participant contact details.

For each imported member:

1. In **Participants → Manage**, complete/correct location, next-of-kin name and next-of-kin phone. Approval is blocked until these are present.
2. Generate a reset code and share it privately. The participant uses **Forgot password → Use your reset code** to set their own password. Imported accounts have no shared or known password.
3. Approve the account, issue its verification token, and assign slots.
4. The participant signs in once with phone, password and token. Later logins need only phone and password.

## Render deployment

This is a server application. Do not deploy it as a Render Static Site.

1. Extract the ZIP. Push the contents of this folder (with `package.json` at repository root) to a **private** GitHub/GitLab repository.
2. Create a Neon PostgreSQL project. Copy the pooled and direct URLs into your own secret settings.
3. In Render choose **New → Blueprint**, connect that repository and select `render.yaml`. It defines a paid Starter web service and a cron job; Render displays the costs before creation. Pre-deploy migrations require a service plan supporting pre-deploy commands. For a service without that feature, run migrations manually in a shell before accepting traffic.
4. Set these web-service variables:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Neon pooled PostgreSQL URL with TLS |
| `DIRECT_URL` | Neon direct PostgreSQL URL with TLS |
| `AUTH_SECRET` | Generated by Blueprint; retain between deployments |
| `AUTH_URL` | Exact HTTPS Render web-service URL, no path |
| `AUTH_TRUST_HOST` | `true` behind Render’s trusted proxy |
| `APP_URL` | Same HTTPS web-service URL |
| `ADMIN_PHONE` | Real, unique admin mobile in `+233…` format |
| `ADMIN_EMAIL` | `admin@ransusu.com` |
| `CRON_SECRET` | A separate random secret; exactly the same on web and cron services |

5. Set `APP_URL` and `CRON_SECRET` on the cron service as well. Keep both web and cron pointed at the same application URL. The cron script calls the protected web endpoint; it does not connect to the database itself.
6. Deploy. The web build runs `npm ci --include=dev && npm run build`; pre-deploy runs `npm run db:migrate`; startup runs `npm start` and binds Render’s `PORT`.
7. Open the web service’s Render shell, run `npm run db:seed`, store the one-time password, then run `npm run db:import`. These are deliberate setup commands, not commands that reset accounts on every deploy.
8. Visit `/login`, sign in as `superadmin`, change the password and complete participant onboarding.
9. Configure notification delivery below. Confirm a test notification reaches your own phone/email before onboarding the group.

When adding a custom domain, update `AUTH_URL` and `APP_URL` on the web service and `APP_URL` on cron to the new HTTPS origin, then redeploy. Participants open the same public HTTPS URL from their phone browser.

Official references: [Render Next.js deployment](https://render.com/docs/deploy-nextjs-app), [Neon Prisma connections](https://neon.tech/docs/guides/prisma), [Auth.js credentials](https://authjs.dev/getting-started/authentication/credentials).

## Payments and accounting

Collection details are displayed on the landing page and payment instructions:

**Telecel Cash · 0507039821 · Hammond Ahenfo**

Participants send money using Telecel Cash, MTN MoMo or AT Money, choosing a cross-network transfer where their provider requires it. This app does **not** debit a wallet or initiate a mobile money transfer. It records a participant’s claim and the admin verifies it against the actual collection-account statement.

- GH₵22 daily **per active assigned slot**.
- Each submitted payment is between GH₵22 and GH₵110, to two decimal places.
- The total of pending plus verified submissions for one member on one Ghana calendar day cannot exceed GH₵110. Rejected submissions do not consume this allowance.
- Amounts are stored as integer pesewas, avoiding floating-point money totals.
- Each transaction ID is normalized to uppercase and globally unique. A duplicate cannot be submitted for another member or date.
- Submissions are recorded for the current Ghana day, never an arbitrary client-supplied date. Reviewed payments retain their original contribution date.
- Only verified payments affect collection totals. Pending is gold; verified is green; unpaid is gray.
- Confirm/reject transitions are atomic, and a second review cannot count a payment again. All financial records are retained when access is rejected.
- A member with multiple slots receives paid status on as many slots as their verified amount covers, in ascending slot-number order. One GH₵22 payment never makes all their slots green.
- Additional slots require an admin assignment. The board refreshes every 20 seconds and on successful changes; this is polling, not a WebSocket service. Dragging into an occupied slot is rejected. The dropdown form is the keyboard/touch alternative.
- If an admin assigns more than five slots to one member, the required amount can exceed the GH₵110 daily limit. The cap remains enforced; resolve the slot assignment with the member before assigning that many slots. The app does not silently raise your stated payment cap.
- Expected collection and the community board reflect **current** active assignments. They are not historical slot-ownership snapshots. Reports sum verified payments by contribution date; custom ranges are inclusive. Week means Monday–Sunday in Ghana time.
- CSV export neutralizes spreadsheet-formula prefixes. Excel uses typed numeric amounts. PDF uses a standard ASCII-compatible font and replaces unsupported glyphs with `?`.

## Access, tokens and password recovery

Every private page and server mutation checks the database user, current approval status and session version. Participant DTOs exclude other members’ phones, kin details, access tokens and transaction records; the community board exposes names and slot status as requested. Admin operations also check the role at the point of mutation.

Participant verification tokens are generated with 80 bits of cryptographic randomness, last 90 days, and are stored only as SHA-256 hashes. They are required only for the first successful participant sign-in. Activation is stored in PostgreSQL, so later logins on any device need only phone and password. A used or expired token cannot activate an unactivated account. Reissuing revokes earlier tokens and existing sessions and resets activation. Deactivating a token also resets activation; issue a new token before the participant can sign in again. Password resets retain existing activation. The admin sees the raw code only once and shares it privately. Reset codes use the same entropy, expire after 30 minutes and can be consumed once; generating another code invalidates previous open requests. Passwords are bcrypt-hashed with cost 12. Account/IP-based public attempt limits persist in PostgreSQL. Password and access changes invalidate sessions using `sessionVersion`.

A password-reset request always gives the same account-existence-neutral public response. The admin issues the code from **Access & tokens**. The participant enters phone, reset code, new password and confirmation on `/forgot-password`.

## Reminder and notification delivery

The cron service runs every five minutes, all day. It generates due reminders in the ten-minute windows starting at **18:00, 18:30 and 18:50 Africa/Accra (UTC)**. Each reminder is unique for member/day/time; rerunning a job does not duplicate in-app reminders. Only approved members with occupied slots and an outstanding verified balance are reminded. Pending claims remain outstanding until verified. Disabling reminders stops new daily reminders but does not discard other notification deliveries.

All notifications appear in-app. External deliveries use an outbox with claims, stale-claim recovery, bounded retries and at most ten deliveries per invocation. SMTP is built in for email; SMS and WhatsApp use your provider adapter.

### Email over SMTP

Add to the **web service**:

```dotenv
SMTP_HOST=smtp.your-provider.com
SMTP_PORT=587
SMTP_USER=your-user
SMTP_PASSWORD=your-secret
EMAIL_FROM="R&A SUSU LTD <notifications@your-verified-domain.com>"
```

Port 465 enables implicit TLS; 587 requires STARTTLS. Set each user’s email in account settings. Email deliveries without a recipient email are marked skipped. SMTP is at-least-once: a crash after sending but before recording success can cause a retry; a stable Message-ID helps recipients identify it.

### SMS / WhatsApp adapter

Set `NOTIFICATION_WEBHOOK_URL` to an HTTPS service you control and `NOTIFICATION_WEBHOOK_SECRET` to its shared bearer secret. The adapter translates this payload to your chosen provider (e.g. an approved WhatsApp Business/SMS integration):

```json
{"channel":"sms","to":"+233…","message":"Your GH₵22.00 contribution is due before 7 PM."}
```

The app sends `Authorization: Bearer …` and `Idempotency-Key: …`. The adapter **must deduplicate** that key, validate the bearer secret, return 2xx only after durable acceptance, and use provider credentials outside this app. WhatsApp requires the provider’s approved templates/consent process. A delivery error is retried up to five attempts. Unconfigured channels remain queued rather than falsely appearing sent. If no SMTP is configured, the same adapter may handle `email` messages.

The cron calls `POST /api/jobs/reminders` with `Authorization: Bearer CRON_SECRET`. Never expose this secret to client components. In production, monitor cron failures and `Delivery` rows with `FAILED` status, configure database backups and test restore/recovery with your Neon plan.

## Checks

```bash
npm run typecheck
npm test
npm run test:integration
npm run build
TEST_HTTP=1 npm run test:integration
npm audit --omit=dev
```

The PostgreSQL integration runner creates and destroys its own temporary database using the development-only `embedded-postgres` package. It cannot point at your Neon database. With `TEST_HTTP=1`, first build the application; the test also starts a temporary production HTTP server and tests real Auth.js login and role restrictions. Normal `npm test` runs validation tests and skips database tests unless launched by the isolated runner.

See `VERIFICATION.md` for the completed checks and the deployment-dependent checks still required. No software can be guaranteed error-free; production acceptance requires exercising your own Render/Neon deployment and delivery providers.

## Login troubleshooting

See UPDATE-DEPLOYMENT.md for private login rejection categories and safe redeployment steps. Imported participants must set a password using an admin-issued RST reset code before their first RAS-token login. Re-registering an imported phone never overwrites its existing password. Codes copied with spaces, newlines or typographic hyphens are normalized; meaningful code characters must still match.
